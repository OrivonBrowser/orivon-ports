# `apps/seedit/`: seedit as an Orivon app

## About this build

**A community build by Orivon of seedit, not the official seedit.** seedit is a serverless, adminless, decentralized alternative to Reddit on Bitsocial: a community is run by its owner's node, and every person reads and posts through a node of their own. This directory holds the recipe that builds it to run in Orivon; the upstream project did not make this build. Status: early access. It starts its own Bitsocial node, the one the desktop app starts in its main process.

What this build changes for the person using it: nothing in the app. It is upstream's desktop renderer, so it keeps the desktop app's settings (the node's WebSocket address, the data path, the link to the node's web UI) and talks to a Bitsocial node on this computer. The page starts that node itself, from the files served with the app, and it runs while a seedit tab is open.

Known gaps in this build:

- **The node runs while a seedit tab is open.** The desktop app's node lives in its main process; here it is a Worker the page starts, and Orivon ends it when the last page of seedit closes or navigates. A community you host answers other people only while a tab of seedit is open. A reload keeps the node when another seedit page (the dashboard, a second tab) stays open, and starts a new one, with the same communities, when none does: the page that starts it is at its first screen in 6 to 22 s on the measured runs, after the Worker has removed any database lock directory the ended node left.
- **A community may not be reachable from other computers behind a router.** The node is told it is `private` by AutoNAT and announces no address; a reader outside your network finds the community only through a relay or a forwarded port, which the node does not set up yet. seedit's own "not reachable from browsers" warning for a hosted community never shows in this build: upstream draws it only for an RPC on port 9138, the desktop's own, which 5chan's node holds here, so seedit's is on 9148.
- **Traffic totals depend on the node.** The p2p stats tab and the dashboard show peers, the peer id, the repository size and, from a node whose `/health` names `bandwidth`, the bytes received and sent since it started and the current rates (the node counts the wire bytes of its TCP sockets); a node without the feature reads "unknown".
- **imgur and imgbb depend on those sites' own upload pages.** Each page is driven in a `<webview>` nobody sees, as the desktop drives it in a hidden window; a site that shows a captcha or a login to an automated page fails the upload, and the app goes on to its next provider as on the desktop. imgur's page uploads as soon as a file is chosen and shows the picture on the post's page, which none of the desktop's selectors reads, so this build reads that picture too (see the design note on imgur). A visitor in Europe sees imgur's consent dialog over the page; it does not stop the upload. catbox needs no page (a direct request, as the desktop makes it). Forge uploads need the Turnstile token below.
- **Forge's Cloudflare check is the person's to pass when Cloudflare asks.** The token comes from Turnstile's widget in a `<webview>` nobody sees; when Cloudflare wants the person to act, the view appears in the middle of the window, 340 by 120 pixels under a "Forge Images" title with a close button, as the desktop's window does. A closed view, or no answer in two minutes, fails the Forge attempt: seedit says the upload failed (Forge is the only host in its default mode, and Random mode goes on to the next one), as on the desktop.
- **Notifications are the page's own, and Orivon v0.1.0 refuses an installed app.** An app whose manifest holds grants is never asked and may not show notifications there: the preferences switch reads `denied`, `testNotification` answers `{ success: false, reason: 'denied' }` and `showNotification` shows nothing (measured in the v0.1.0 shell). A site Orivon does ask about gets the person's answer: the click on the switch, `testNotification` and the first `showNotification` raise the prompt. A click on a notification opens the post it names in this tab, and an https address in a new tab.
- **An embed is shown in a `<webview>`, so a site that checks which page frames it can refuse.** Twitch's player is given the app's host as its `parent` and has no parent frame to confirm it. The sites an embed can open are the ones in `web.embed.origins`; one that is not there stays blank. The window of a board's spam-blocker challenge draws the challenge page in an `<iframe>` too, and it is shown the same way for the challenge's own address (`https://spamblocker.bitsocial.net`); a board owner's own address for the challenge stays blank, though "Finish Challenge" still answers. A link to a PDF is the one embed whose frame can name any site (the component frames the link itself): it stays blank unless the PDF is on a site in that list.
- **A "settings upgrade available" dialog appears on a new account** and offers two HTTP routers that are newer than the desktop preload's list. It is upstream's own check against its current defaults.
- **Two close-button pictures 404 in that dialog** (`/assets/assets/buttons/close-x-button-large.png` and its hover picture): upstream's stylesheet resolves a relative path from the wrong folder. The desktop app loads the same files by relative path.

The sections below are for people working on the build.

**What this is.** seedit's desktop renderer is the Vite build its web app is made of (`vite build` with `PUBLIC_URL=./`, which `electron:build` runs before Electron's packager takes the folder). Two window values make that build the *desktop* app at run time (`src/lib/p2p-browser-config.ts`): `window.isElectron` and `window.electronApi.isElectron`. With them the page uses a Bitsocial node over RPC; without them it runs libp2p in the page. This port sets both inside Orivon, with the other values `electron/preload.mjs` sets, so the same page needs only a node behind port 9148, which `node-start.js` starts.

## Running it

```bash
orivon-port run seedit      # clone at the pinned commit, build, prepare, serve on 127.0.0.1:8887
orivon-port test seedit     # or: npx vitest run apps/seedit
```

The build runs upstream's pinned yarn (4.17.1, fetched with `npx`, never `corepack enable`) with `ELECTRON_SKIP_BINARY_DOWNLOAD=1` and `--mode=skip-build`, so no native module is compiled, and then upstream's `vite build` with its `build` script's environment. It needs no network after the install.

Open `http://127.0.0.1:8887` in Orivon and accept the prompt. `seedit.orivonstack.eth` works too once the shell is launched with `orivon-port names`' output (the top-level [`README.md`](../../README.md), "Opening it by name instead of by port").

## The seam

`electron/preload.mjs` sets four window values and two objects: `window.electron` (2 members) and `window.electronApi` (11). How this port answers them:

| Member | Answer | State |
|---|---|---|
| `isElectron` (window and `electronApi`) | `true` | works |
| `defaultPkcOptions` | the RPC address `ws://localhost:9148/<key>` and the preload's four HTTP routers | works; the node behind it is the one `node-start.js` starts |
| `defaultMediaIpfsGatewayUrl` | `http://localhost:6483` | works; the node's gateway socket |
| `pkcRpcAuthKey` | the same key as in the RPC address | works (unused by the renderer, kept as the preload has it) |
| `electron.invoke` | the preload's four channels (`get-notification-permission-status`, `get-platform`, `test-notification-permission`, `copy-to-clipboard`); any other channel throws `Unauthorized IPC channel` at once, as the preload does | works |
| `electron.sendNotification` | shows a notification | works |
| `getNotificationStatus` | the page's permission: `'granted'`, `'denied'`, `'not-determined'` for `default`, or `'not-supported'`; when it is not `granted` and a click on a switch came just before, it asks the person first | works for a site Orivon asks; an installed app reads `denied` |
| `testNotification`, `showNotification` | the Notification API; when the permission is not `granted` each calls `Notification.requestPermission()` first and reports the answer | works for a site Orivon asks; an installed app is refused |
| `getPlatform` | `{ platform, arch, version }` with Node's names (`win32`, `darwin`, `linux`; `x64`, `arm64`), read from the browser; `version` is `''` (the desktop sends Node's version string, which nothing reads) | works |
| `copyToClipboard` | the async clipboard; `{ success, error }` | works |
| `isFileOnDisk` | `true` for a `File` and `false` for anything else, as `Boolean(webUtils.getPathForFile(file))` is for a value with no path | works |
| `getNodeReachability` | whether a reader can reach the node, `'public'`, `'private'` or `'unknown'` (the desktop gives AutoNAT's verdict, from its kubo API, five seconds) | works: asked of the node's handle (`window.orivonBitsocialNode`), which asks the Worker, and the handle's last known verdict stands when the Worker is slower than five seconds |
| `automateUploadMedia`, `automateUploadGeneratedMedia` | catbox: a routed request with the form catbox takes; the page passes the `File` itself. imgur and imgbb: the host's upload page in a `<webview>` nobody sees (`webview-upload.js`), with the metadata removed first on the `File` route | works |
| `getForgeTurnstileToken` | the token of Cloudflare's Turnstile widget, run on `http://localhost:50229` in a `<webview>` (`webview-turnstile.js`); rejects with the desktop's error texts | works: a token for Cloudflare's always-pass test sitekey in a real shell run; the real Forge sitekey gets Cloudflare's "Verify you are human" checkbox, which only a person passes (see the design note on the Turnstile token) |

**1 of 13 calls `orivon.*`.** `getForgeTurnstileToken` opens a listener with `orivon.net.listen` to serve the widget's page. The members that need no node are the page's own: the clipboard, `fetch`, `localStorage`, the Notification API. The upload members use the page's `<webview>` element, which the `web.embed` grant allows. The node's page module forks the Worker with `child_process.fork`, and `node-start.js` starts nothing until the page has its permissions (`window.orivon.fs` exists); the bridge's own members do not touch it.

A refusal rejects instead of throwing, because the preload's versions return promises and a call site outside an async function has no `try` to catch a throw. `electron.invoke` is the one throw: the preload throws for an unknown channel before it makes a promise.

## Design notes

**The desktop values are set only inside Orivon.** The page picks its runtime from `window.isElectron`, from `electronApi?.isElectron` and from single `electronApi` members, so outside Orivon none of them may exist, nor `window.electron`. The bridge's first statement is a `return` unless `window.orivon` is an object with a numeric `version`, which every Orivon tab has (v0.1.0 included) and which the hint tests too. The `return` is legal because `compose.ts` splices the file inside a function of its own, so the installer after it never runs: no `isElectron`, `electron`, `electronApi`, `defaultPkcOptions`, `defaultMediaIpfsGatewayUrl` or `pkcRpcAuthKey`, no key in `localStorage`, and the service worker is left alone. `node-start.js` makes the same test: outside Orivon it leaves `fetch` and `WebSocket` as the browser made them and starts no node, and it still gives the module entry its type back at once, so the app runs. The renderer then merges its own web defaults, as upstream's web version does. The hint is tier 1 there, a pill that does not hold the page back.

**The RPC key lives in `localStorage`.** The desktop keeps a 40-character key in a file beside the node's data and puts it in the URL the page connects to. The page has no main process to hand it over, so the bridge makes one (40 characters of a 62-character alphabet, rejection sampling over `crypto.getRandomValues`), stores it as `orivon.pkcRpcAuthKey`, and reads it back on the next load; a stored value that is not 40 letters and digits is replaced, and storage that throws leaves a key for that load only. The node's page module reads the same key from the same place when it starts the node. The key is a bearer secret for the RPC socket on a loopback port; it stays in this origin's storage.

**No service worker inside Orivon.** The page registers a worker at start (`src/index.tsx`, `registerSW`, inside the bundle). The desktop never has one (a `file:` page cannot register it), and a worker here would keep serving one release's files, the bridge among them, after Orivon installs the next, which is the cache-across-a-republish failure. So inside Orivon the bridge removes `serviceWorker` from `navigator`, which the registration and the app's own checks both test for, and unregisters a worker an earlier load registered. This is the bridge's job, not the hook's, because the registration is in the bundle and no upstream byte is edited. The worker file stays in the tree and is never used there. In a real shell run `'serviceWorker' in navigator` is `false`. Outside Orivon the bridge has returned before this, and the worker registers as it does in upstream's web version: the built `sw.js` precaches relative URLs (`index.html`, `assets/...`), so on a path gateway (`/ipfs/<cid>/`) it takes the app's own folder as its scope and finds its files there (the plain-browser check loads the tree at `/` and under `/ipfs/<cid>/`, and the worker activates in both).

**The `/#` redirect.** Upstream's page has an inline script that sends a path with no hash, such as `/u/name`, to `/#/u/name` from the root of the host. It cannot run inline under the served policy, and moved unchanged it would send a deep link on a path gateway out of the app's folder. The hook writes it again as `orivon/inline-script-1.js`: the same test, with the app's folder taken from where that file is itself loaded (`new URL('../', document.currentScript.src)`), so at the root of a host it does what upstream's does. The other inline script (the static-shell paint) moves byte for byte, where it stood. The hook throws unless it finds two inline scripts and exactly one redirect.

**Notifications.** The desktop answers `'granted'` wherever the operating system has no switch of its own for the app, and reads the real one only on macOS, where an app nobody asked yet reads `'not-determined'`. A page has the Notification API's `permission`: `granted`, `denied`, or `default` for nobody asked. The bridge answers `granted` for `granted` and `denied` for `denied`, and `'not-determined'` for `default`: it is the macOS case of nobody asked, so the preferences keep the switch off and do not claim that notifications are on (answering `granted` there would have `new Notification` show nothing until the person allowed it). Reading the status never asks. What asks is the person's click on a switch (a trusted `change` event on a checkbox in the second before `getNotificationStatus` is called, which is how the preferences call it; `testNotification` is never called by the page) and `testNotification` and the first `showNotification`, which call `Notification.requestPermission()` when the permission is not `granted` and report what the person answered. Orivon reads a site nobody has answered for as `denied`, the same as a blocked one, so the bridge cannot tell them apart and the click is the only place a person can grant; a site the person blocked is not asked again. Orivon asks only for a site it knows as a website. An installed app, which holds grants, is refused with no question (`src/main/sessions/site-notifications.ts` in v0.1.0), so the switch there reads `denied` and nothing is shown. A click on a notification passes its `url` to `shell.openExternal` on the desktop, and seedit's own `url` is a route of the page (`/#/p/<community>/<post>`), which that call rejects, so a click does nothing there. The route is the intent: a route of this page is opened in this tab, which is brought to the front, an `https:` address opens in a new tab with no opener, and anything else is ignored.

**`getPlatform` returns Node's names.** The notification settings compare the answer with `'darwin'` and print it inside a sentence ("check your system's (linux) notification settings"), as if it were the name, while the desktop's main process answers the object; so the object prints as its `platform` (a non-enumerable `toString`), and a refusal reads "(linux)", never "([object Object])". The browser's own names (`MacIntel`) would never match. The platform is read from `navigator.userAgentData`, `navigator.platform` and the user agent, and `arch` is `arm64` when the browser reports an ARM architecture and `x64` otherwise.

**The node link.** The desktop sends exactly `http://localhost:50019/webui/` to the system browser. Here a capture-phase listener on `click` and `auxclick` stops that navigation and opens `orivon/node/index.html`, served with the app, in a new tab. That page's frame, wording and look are seedit's own (its built stylesheet and variables, in `hooks.mjs`), and it wears the theme seedit wears (`bridge/node-theme.js`: the same stored choice, applied the way seedit applies it, read again on each load); what it draws is the node app's dashboard module, `node-dashboard.js` of the node bundle, which `bridge/node-dashboard.js` mounts with this app's name and the two sections it offers. `node-start.js` finds the node already answering, and the module draws the numbers the node's page API gives (state, peer id, peer count, reachability, repository size, the two sockets) every five seconds. Being a second page of the origin, it also keeps the node running across a reload of seedit's page.

seedit shows no board manager section: the board manager is a tool of 5chan's boards, and this app does not name it. It names `listing-signature`, the signed request alone: seedit's own "Propose a community" link opens a GitHub issue from a template that has no entry, no signature and no check, so the dashboard offers only what that link lacks. Each community the node hosts has a card with a choice of route (`seedit-directories/` of `bitsocialnet/lists`, read live as the app reads them) and "Prepare the request", which has the node sign an entry with the community's key and shows the whole text, entry, signed message and a one-line command that verifies it from the community's address, before anything is copied. "Copy the text" puts it on the clipboard to paste into seedit's issue. The card has no requirements and no button that opens GitHub: seedit's directories set no requirement a community's record can be checked against, and the link is the app's own. It reaches only raw.githubusercontent.com, which the manifest's `https` grant already covers. The node app's README, sections The listing calls and The node dashboard, has the rest.

seedit also names `name`, a card for each community the node hosts that gives it a `.bso` or `.eth` name, which seedit helps with only by words: its Community Settings has an Address box and a `[?]` that says to set the text record `bitsocial` on the name by hand and then enter the name, and it checks nothing. The card shows that record exactly (the text record `bitsocial` of the ENS name, holding the community's public key) with a copy button for each part, checks that the name points at the community as the node's own name resolvers read it, and, on a page that has a wallet, prepares the transaction that sets the record and sends it only when the person presses the button that asks the wallet. When the name points at the community it says to set the address in seedit's Community Settings (the Address box): the card changes no address, since seedit's own settings do. It reads Ethereum through the node, so the manifest needs nothing new; the node app's README, sections The name calls and The node dashboard, has the rest.

**The page starts the node.** `node-start.js` calls the node app's page module (`node-client.js`, the node's own build output) with this app's ports and the key the bridge made. The module tries `ws://localhost:9148/<key>` first and uses a node that answers; otherwise it forks the Worker (`node/server.mjs`), which runs Orivon's IPFS node, the kubo facade, the gateway socket and pkc-js's RPC server behind the key guard, and resolves once the RPC socket listens. Nothing starts on a page that has no permissions yet or is not isolated (`window.orivon.fs` is absent until the person has answered the consent prompt), and the page reloads after the answer, so the first load of the first run does not leave a Worker behind. A start that fails is made again after 4, 8, 16 and 30 seconds, five starts in all, and `ready` settles with the handle of the first that works, or with `null` and the last reason after the fifth; it never rejects. The handle is `window.orivonBitsocialNode`, whose `error` holds the reason once the fifth start has failed. The key is read from the bridge's `window.pkcRpcAuthKey`, or from this origin's `localStorage` on a page the bridge did not run on (the dashboard).

**The bundle is shown while the node starts.** The RPC client in the bundle (pkc-js, `clients/rpc-client/pkc-rpc-client.js`) gives its connection 20 seconds from its first call (`_timeoutSeconds`, line 62; the wait is the `pTimeout` at lines 195 to 207), then sets its state to `failed`, emits `error` and rejects the calls that waited, and the community hooks never ask again, while its WebSocket goes on retrying. A connection that opens inside those 20 seconds costs nothing, and a call sent on it waits 300 seconds for its answer (`_callTimeoutMs`, line 67; the `pTimeout` at lines 171 to 176, which starts once the connection is open); `rpc-websockets` under it sets no timer on the calls the client sends (it passes none) or on an open connection. So the hook types the bundle's module entry `orivon-held-module`, a type no browser runs, and `node-start.js` gives it back its own type (every attribute kept, `type=module`) as soon as the page is parsed, on every launch: whether the node's files are on this computer or have still to arrive over the IPFS network, the app is drawn without waiting for the node, and `node-start.js` stands in for the node's RPC socket until it answers. The entry is released while the node starts, across its retries, and when every start has failed. While the node starts, `window.WebSocket` is a proxy that treats only the node's own address (`ws://localhost:9148/<key>`) differently: the socket the bundle makes there is reported open at once and what the page sends on it waits, and the real socket is opened when the node has answered (every event it brings is handed on, and what waited is sent in order) or failed to start. The socket is open and not left CONNECTING because the app takes an RPC that is not connected for a page with no node of its own: the app's "settings upgrade available" dialog opens over it (its two default HTTP routers are the ones the preload's four lack), and "create your own community" sends the person to a download page. Every other socket is the browser's own, and so is every socket once the node has answered. A start that is refused for half a minute (the page was opened again within about that time of the last one closing, which Orivon v0.1.0's shell answers with `revoked`) or a verifier that reads the node's files again costs the app time and not its connection; a node that answers after 270 seconds, when the calls that waited (300 seconds) are about to time out, makes the page load once more, once per tab. A page that has no bundle to release, the node dashboard, says "Starting your Bitsocial node..." once the wait is noticeable (with the file it is on, when a first start has failed and the node's files are read again); if every start fails, the app shows its own connection error after the last retry. A page with no permissions, or outside Orivon, releases the entry at once and stands in for nothing.

**The desktop's kubo calls are answered in the page.** seedit's p2p stats tab (`src/lib/p2p-stats.ts`) and its reachability check call `http://localhost:50019/api/v0/` (the kubo API the desktop's main process runs) for `id`, `swarm/peers`, `stats/bw`, `repo/stat`, `swarm/addrs/autonat` and `version`. Nothing listens on 50019 in this build, so 5chan's node and seedit's do not meet there, and a kubo API that any app granted that port could drive would hand it the node. `node-start.js` wraps `window.fetch` instead: a request to either spelling of that origin never leaves the page. A path under `/api/v0/` goes to the node's page API (`POST /orivon/api/<call>` on the gateway socket, with the RPC key as a bearer token, which answers those six calls and refuses every other with 403); any other path of that origin (the web UI) is 404. A page of another origin cannot use either without the key: the RPC socket refuses a path that is not `/<key>` (a dial with no key or a wrong one closes with 1006), and the page API refuses a request with no key (401) and one whose `Origin` is not an origin the app named (403). The key is the only guard of the RPC socket: a page of any origin that holds it can open the socket, as on the desktop, where it is the only guard too. The page API is on the Worker's socket and not on the Worker's message channel because a page that reused a node, such as the reloaded page, has no handle on the Worker that another page started. `stats/bw` is the node's own count (`TotalIn`, `TotalOut`, `RateIn`, `RateOut`) when its `/health` names `bandwidth`; otherwise it answers null totals, and seedit shows them as unknown.

**The create-community page needs the connection's state at its first render.** seedit's "Create your own community" button opens `/communities/create` only when `usePkcRpcSettings().state` is `connected`, and that page sends the person home from its own first effect when the state it reads is not `connected`. The hook (`@bitsocial/bitsocial-react-hooks`) starts every instance in `initializing` and fills the state in from the RPC client in an effect, so the page's first effect always sees `initializing`: measured in the shell with the node running and the sidebar's own hook `connected`, the address went to `#/communities/create` and back to `#/hot` within 300 ms, in every one of 30 tries. `finishTree` in `hooks.mjs` makes one edit of the built script that holds the hook: its first state is the RPC client's state, `initializing` only when the client has none, which is the value the effect sets a moment later. A page whose client is not connected still sends the person home. The edit is a text match that throws when the built code no longer has that shape, runs once however often the tree is prepared; dropping it loses the create-community flow and nothing else.

**The create page's effect for a made community runs once.** Once a community exists, the create page runs an effect (`community-settings.tsx`, `useEffect` on `createdCommunity`) that alerts, calls `subscribe()`, resets the form store and navigates to the community. Its value list holds `subscribe`, and the hook (`useSubscribe`) memoises its result on its list of errors and on `subscribed`: the first call succeeds and flips `subscribed`, the effect runs again with a new `subscribe`, the call throws `already subscribed` and adds an error, which makes another new `subscribe`, and so on. Measured in the shell: 1,753 and 1,943 passes in 12.4 and 13.5 seconds (150 to 600 a second), every one but the first throwing, and the navigation to the community's page is held off as long (the old page stays mounted under a pending route change). In those 13 seconds the Worker and the node do nothing at all (no broker call from the first second to the fourteenth, `ORIVON_BITSOCIAL_CENSUS=1`): the first signed record came 18 to 21 seconds after the press, against 6.4 with the effect run once. `finishTree` makes the second edit of the port: the effect's value list becomes the created community alone, so the effect runs once for each community. A text match too, throwing when the shape changes, once however often the tree is prepared. These two are the only edits this port makes to upstream's built code.

**The bridge starts the community the page creates.** The node's RPC `createCommunity` makes a community that stays `stopped`, and seedit never starts one: its page, `@bitsocial/bitsocial-react-hooks` and its desktop main process (a plain `PKCWsServer`) have no `start` call, so on the desktop too a community made in the page waits until something else starts it (bitsocial-cli's `community create` and 5chan's create-board form start theirs). In this port a post to such a community waited for a signed record that no one was making, and failed after five minutes. `node-start.js` wraps `WebSocket` for the RPC address only: when the node answers a `createCommunity` the page sent, it sends `startCommunity` for that address on a socket of its own and closes it at the answer (the node keeps the community started). On a loaded machine the first signed record then takes about four minutes (measured, node with ten default communities loading), and a post made before it waits as `PENDING`. The node app must not start created communities itself, because 5chan's form calls `start` on the one it made and a second start is an error. A started community comes back by itself: pkc-js's RPC server starts again, at every boot, each community its state database lists as started (the node's log says `Successfully auto-started` about six seconds after `ready`), so the bridge's start runs once per community.

**The node is a pinned build output, not imported code.** `build/fetch-node-bundle.mjs` runs after the app's build (`build.also`) and copies `node/` (the Worker's loader `server.mjs`, its packed script and `sqlite3.wasm`), `node-client.js`, `node-dashboard.js` and `bin/` (the IPFS node component, its packed program and its licences) from a build of `apps/bitsocial-node` (`BITSOCIAL_NODE_BUNDLE_DIR`, or that build's own output folder) into the served tree. Each file must match its size and sha256 in `build/node-bundle-pin.mjs`, and the files under `bin/` must be the component `apps/bitsocial-node/build/node-component-pin.mjs` pins. A mismatch fails the build with the way to move the pin on purpose (`node build/fetch-node-bundle.mjs --pin` after a rebuild of the node). Nothing of the node app is read when the page runs: the copy is this app's own files, and two apps that run the node carry one copy each.

**imgur and imgbb run as the desktop's hidden window does, in a `<webview>` nobody sees.** The desktop opens the host's upload page in a window that is never shown, puts the file on the page's file input, clicks submit, and reads the link off the page every 500 ms (`electron/media-upload-recipes.js`, `media-upload-automation.js`). `webview-upload.js` takes each step and each selector, message and timeout from there, so the app's own provider order, the blocked-page fallthrough and the error texts its orchestrator reads (`parseAttemptMetadata`) behave as on the desktop. What differs is the means. The element is attached on `about:blank` and then sent to the page, which makes a refused origin reject the load instead of ending the element. The page is another site's, so the file reaches its input from inside it: the bytes are sent in pieces of a mebibyte through `executeJavaScript`, put together as a `File`, set on the input with a `DataTransfer`, and `input` and `change` fire, which is what a chosen file fires. The click is the page's own `element.click()` with a user gesture, which imgbb's button accepts. A poll that fails once (the page replacing itself after the click) is "no link yet". The element is a fixed 800 by 600 box at the top left, fully transparent, not clickable and muted, and it is removed when the upload ends, however it ends. The uploads and the embeds draw on the same grant, `web.embed`: only the origins in `orivon.json` load, and a document at any other origin is refused, which for an upload page that redirects elsewhere is a failed load.

**imgur is read from its post page.** imgur's page does not have the shape the desktop's selectors expect: choosing a file uploads it at once, the page moves to `/a/<id>`, the copy-link field there holds the post's address and no `i.imgur.com` anchor exists, so the desktop's four candidates find nothing and its recipe times out. `webview-upload.js` keeps the desktop's candidates first and, only when none answers and the page's path is a post (`/a/` or `/gallery/`), reads the one `<img src="https://i.imgur.com/...">` the page shows. The submit button, which exists only after the upload and opens the page's own upload popup when clicked, is looked for after the file as on the desktop; where there is none, the upload goes on to wait for the result and gives the desktop's "No submit button found" message only if none comes.

**Every `File` is "on disk", so the metadata is removed in the bridge.** The renderer asks `isFileOnDisk(file)` first: a file with a disk path goes to `automateUploadMedia`, whose bytes never pass through the renderer and which main strips of camera and location metadata (`electron/strip-media-metadata.js`); any other goes to `automateUploadGeneratedMedia`, which the renderer strips itself and which main limits to 20 MiB. Every `File` seedit holds comes from its file picker or a drop (`useDropzone` in `src/views/submit/submit.tsx`), which on the desktop are the files with a path. So the bridge answers `true` for a `File` and takes the first route: `stripMetadata` in `webview-upload.js` (written from the JPEG, PNG and WebP container formats, not copied) removes the metadata, a rotation survives as the one small tag it needs, and a file that is not one of the three, or that cannot be read to its end, is uploaded as it is, so stripping never blocks an upload. The generated route sends the bytes as they are, with the file named as main names its temporary file (the last path segment, no `..`, other characters replaced by `_`).

**An embed frame stays in the page; its element is added beside it.** The built page renders each click-to-open embed as an `<iframe>` its component owns, and a framework removes a node from its own parent: replacing the frame with another element would make that removal throw. So `webview-embeds.js` hides the frame (`display: none`) and puts a `<webview>` after it with the frame's class, so the app's own styles size it, a zero-weight 100% by 100% fallback for the frame's own width and height hints, its title, and its address. The address is the frame's `src`. The four embeds that carry inline content (X, Reddit, TikTok, Instagram: a quote block and the site's widget script) are shown from a `data:` page that holds the same content, and the widget then opens a frame of its own site, which is why those sites are in `web.embed.origins` too. Instagram's component writes its script address without a scheme (`//www.instagram.com/embed.js`), which a frame's inline content resolves against the page that holds it and a `data:` page cannot, so the script writes the scheme out. A frame that sends its own origin as the referrer (YouTube's) gets the app's origin as `httpreferrer`. A window an embed asks for opens as a tab, for a secure address only, as the desktop sends one to the system browser. A frame removed by the app takes its element with it, and one whose `src` the app changes is followed. Outside Orivon `<webview>` is an unknown element and nothing here runs. seedit has no Vimeo embed, so Vimeo is not in the list; its PDF embed frames the link itself, whatever the site, which no exact origin list can name.

**The Turnstile token is the desktop's, with its own window made of a `<webview>`.** Forge's upload API takes a Cloudflare Turnstile token, and Turnstile issues one only to a hostname the sitekey allows, so the page's own origin can never get one and the desktop's main process (`electron/forge-turnstile.js`, the file 5chan's desktop has too) runs the widget in a window it opens on `http://localhost`. `webview-turnstile.js` does the same in three parts. **The page is served by the page that asks, not by the node's Worker.** On a call it opens `orivon.net.listen({ port: 50229, scope: 'local' })`, answers `GET` and `HEAD` of `/forge-turnstile` with the widget's page (404 for any other path, 405 for any other method, a request head over 8 KiB or silent for 5 s closed), and keeps the listener open for ten seconds after the last call in flight ends, so calls that follow one another reuse it; a call that finds the listener closing waits for the port to be free. Nothing is added to the Worker, so the node bundle and its pin are as they were. A second page of seedit that finds the port taken goes on to load it, because the first page's listener answers. **The page is shown in a `<webview>` at the exact origin `http://localhost:50229`**, loaded after the element is attached on `about:blank` and read with `executeJavaScript`: `window.turnstileResult` for the answer and `window.turnstileInteraction` for the moment Cloudflare wants the person to act. The load is not awaited (the desktop waits for `dom-ready` for the same reason: the load ends only once Cloudflare's script and frame have), and the page's own clocks (15 s for the script, 30 s for a token, 120 s once the person is asked) and the 180 s backstop are the desktop's. **The view is invisible until Cloudflare asks.** Then it moves to the middle of the window at 340 by 120 pixels under a 28-pixel title bar that says "Forge Images" and holds a close button, the one visible change this port makes, standing for the desktop's window and its close box; closing it ends the call as closing the window does. The widget's page is written from what the desktop's page does, with the desktop's options (`appearance: 'interaction-only'`, `retry: 'never'`, `refresh-expired: 'never'`) and error texts, so the preload's `Error(error)` reads as on the desktop. A failed call is a failed Forge attempt: `uploadToForge` reports `Turnstile check failed: ...`, and the preferences' mode decides what follows (the only host in the default mode, the next one in Random mode), as on the desktop. The widget seedit draws in the page itself (`getTurnstileToken` in `src/lib/media-hosting/forge.ts`) is used only where `getForgeTurnstileToken` is absent, as in a browser, and stays as upstream has it. The page is served with a policy of its own: `default-src 'none'`, its one inline script admitted by a nonce made for the response, and Cloudflare's origin for the script and its frame. **Cloudflare's frame is a document of another origin inside the shown page**, so `https://challenges.cloudflare.com` is in `web.embed.origins` beside the page's own; a subresource is the page's business, and Forge's API and media hosts are reached by `https.connect` as any host is.

**What differs from the desktop's window.** Its partition is in memory and Electron's own user agent is kept; this view lives in the app's `persist:embed-` partition, which the shell chooses for every `<webview>`, so Cloudflare's storage for `localhost:50229` survives a restart of the shell. The desktop's window is centred on the screen and a child of the app's; this one is centred in the app's window. A reload, a crash of the page and a closed view end the call with the desktop's three texts. A shell that never attaches the view fails the call after 30 s with `Turnstile page failed to load: the page could not be shown`, which has no desktop counterpart. The grant names the exact origin `http://localhost:50229`, which the shell shows whatever listens there, so a program of this computer that holds the port while no page of seedit does could show its own page in the view; the view has no `orivon.*` and a program that can bind a loopback port can already do what that page could. A `http://*.localhost:50229` pattern would show only this app's own listener; its host name is not `localhost`, and *provisional*: no run has asked Cloudflare whether Forge's sitekey allows it.

**The upload page and the helper scripts are not in the bridge file.** A bridge is one spliced script and the size limit is 500 lines, so the three `webview-*.js` files sit beside it and `hooks.mjs` copies them into the served tree and loads them last in the head. The bridge reads `window.orivonWebviewUpload` and `window.orivonForgeTurnstile` when a member is called, not when it is installed, and rejects with a plain message when one is missing. Nothing in these files names seedit (the Turnstile script takes its port from the bridge). `webview-turnstile.js` is 5chan's file byte for byte: each app stands alone, so it is a copy, as `webview-upload.js` and `webview-embeds.js` are copies that have since taken their own app's differences, and the two are kept the same by hand.

**Ports.** Every app that runs a node needs its own, so two of them run at once. seedit: RPC 9148, gateway 6483, node API 50129, Turnstile page 50229, peer range 4011-4020; 5chan has the block below it (9138 and so on). 50019 is the desktop's kubo API port, which the page answers without a socket (see above) and the manifest names nowhere. The node API and the Turnstile ports are this port's own: they are named in `tcp.listen.local` and, for the Turnstile page, in `web.embed.origins`, because `*:*` never reaches loopback and each port is named. The connect list names the RPC, gateway and node API on `127.0.0.1` and `localhost` (the page dials the first two, the Worker the third) and two DNS resolvers (`1.1.1.1:53`, `1.0.0.1:53`) the node's own lookups use, as the node app's manifest does. `grants.test.ts` fails if a port or a connect pattern of this manifest is also in 5chan's.

**`fs.quotaBytes` is 10 GiB.** It is the size Kubo's datastore is capped at by default (`Datastore.StorageMax`, 10 GB), which the node's blockstore, the pinned community data and the hosted communities' databases share, and the node's SQLite files live in it. *Provisional*: a real use moves it.

**`crossOriginIsolated: true`.** The node's page module needs it, as the node app's manifest declares it: the Worker's SQLite engine is WebAssembly with shared memory. Its cost is the two headers on every response: cross-origin subresources load without credentials (`credentialless`), and a popup the page opens is in its own browsing context group. `node-start.js` starts nothing on a page that is not isolated.

**`https.connect` is `*:*`.** Posts link any site, and the app's own requests go to its stats provider, name resolvers, router lists and catbox. Orivon's routed request replaces the header rewrite the desktop's main process does: it sends no `Origin` unless the app sets one.

## What it needs from orivon-mvp

Catalogue ids from `test/app-behaviours/catalogue.md` that this port relies on; a red `[app:<id>]` test is this port's breakage:

- `routed-websocket-reaches-granted-loopback-port`: the RPC connection to `ws://localhost:9148`.
- `routed-fetch-reaches-granted-hosts`: posts, the stats provider, name resolvers and catbox are reached with no CORS check.
- `routed-fetch-sends-no-origin-by-default`: the node's APIs and catbox refuse a foreign `Origin`.
- `routed-fetch-sends-formdata`: the catbox upload.
- `routed-fetch-loopback-grant-covers-both-spellings`: the node API and the gateway answer on `localhost` and `127.0.0.1`.
- `wildcard-host-never-reaches-loopback`: why every loopback port is named.
- `page-media-from-own-listener`: the gateway's images and video, which load because an app with a listen grant is served the loopback sources in `img-src` and `media-src`.
- `localstorage-survives-restart` and `indexeddb-survives-restart`: the RPC key, the account and the caches.
- `cross-origin-isolated-when-declared`: the isolation the manifest asks for.
- `clipboard-write-without-prompt`: the copy buttons.
- `window-open-noopener-opens-tab`: outbound links, the node link and a notification's https address.
- `webview-popup-reaches-the-app`: a window an embed asks for, which `webview-embeds.js` opens as a tab.

Behaviours of `web.embed` that the catalogue does not state and the two scripts rely on (measured in a real shell, with a loopback page standing for each site and against the real imgbb, imgur and YouTube): a `<webview>` that is fixed, transparent, not clickable and muted still loads its page and reports `document.visibilityState` as `visible`; `executeJavaScript` runs in it, with and without a user gesture; a file set on a page's `<input type="file">` with a `DataTransfer` fires `input` and `change` and the page uploads it; `loadURL` of a document at an origin outside `origins` rejects; the `httpreferrer` attribute is the `Referer` the shown page's request carries and what `document.referrer` reads there; a `data:` page is admitted, and a widget script it loads from a granted origin runs. None has a row.

Behaviours of `web.embed` and `orivon.net.listen` that the Turnstile script relies on, measured in a real shell run with Cloudflare's own widget and seedit's own submit page: a page the app serves from its own `orivon.net.listen` (a hand-written HTTP/1.1 answer per connection, `Connection: close`) loads in a `<webview>` at the exact origin `http://localhost:<port>` when the manifest names that origin, with no local pattern; the widget's frame loads from `https://challenges.cloudflare.com` once that origin is in `origins`; a `<webview>` inside a fully transparent, unclickable box behind the page reports `document.visibilityState` as `visible`; `executeJavaScript` of an expression that is a promise waits for the promise. Against the real Forge API from the page (`https.connect` `*:*`): an XHR with an upload listener, as `uploadToForge` sends it, gets the API's own HTTP answer (a token made with Cloudflare's test sitekey is refused with `403 turnstile_failed`, and the submit page says "Upload failed: missing or invalid Turnstile token"), so the request is not stopped by a missing CORS answer. None has a row.

Three behaviours the catalogue does not state are relied on: a classic script the app serves can remove `navigator.serviceWorker` from the page before the bundle runs (measured in a real shell run, not by CI), a `ws://localhost:<port>` dial reaches a listener bound on `127.0.0.1` only (the shell's dial tries both address families, and the page's dial to the node's RPC socket connects), and a page's `Notification` permission and `window.focus()` behave as the bridge reads them in the shell. None has a row.
