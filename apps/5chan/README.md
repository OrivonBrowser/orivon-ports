# `apps/5chan/`: 5chan as an Orivon app

## About this build

**A community build by Orivon of 5chan, not the official 5chan.** 5chan is an anonymous imageboard on Bitsocial, with no server and no admin: a board is a community whose owner runs a node. This directory holds the recipe that builds it to run in Orivon; the upstream project did not make this build. Status: early access. It starts its own Bitsocial node, the one the desktop app starts in its main process.

What this build changes for the person using it: nothing in the app. It is upstream's desktop renderer, so it keeps the desktop app's settings (the node's WebSocket address, the data path, the link to the node's web UI) and talks to a Bitsocial node on this computer. The page starts that node itself, from the files served with the app, and it runs while a 5chan tab is open.

Known gaps in this build:

- **The node runs while a 5chan tab is open.** The desktop app's node lives in its main process; here it is a Worker the page starts, and Orivon ends it when the last page of 5chan closes or navigates. A board you host answers other people only while a tab of 5chan is open. A reload keeps the node when another 5chan page (the dashboard, a second tab) stays open, and starts a new one, with the same boards, when none does: the page that starts it is at its first screen in 6 to 22 s on the measured runs, after the Worker has removed any database lock directory the ended node left.
- **A board may not be reachable from other computers behind a router.** The node is told it is `private` by AutoNAT and announces no address; a reader outside your network finds the board only through a relay or a forwarded port, which the node does not set up yet.
- **Traffic totals depend on the node.** The P2P stats panel and the dashboard show peers, the peer id, the repository size and, from a node whose `/health` names `bandwidth`, the bytes received and sent since it started and the current rates (the node counts the wire bytes of its TCP sockets); a node without the feature reads "unknown".
- **imgur and imgbb depend on those sites' own upload pages.** Each page is driven in a `<webview>` nobody sees, as the desktop drives it in a hidden window; a site that shows a captcha or a login to an automated page fails the upload, and the app goes on to its next provider as on the desktop. imgur's page uploads as soon as a file is chosen and shows the picture on the post's page, which none of the desktop's selectors reads, so this build reads that picture too (see the design note on imgur). A visitor in Europe sees imgur's consent dialog over the page; it does not stop the upload. catbox needs no page.
- **Forge's Cloudflare check is the person's to pass when Cloudflare asks.** The token comes from Turnstile's widget in a `<webview>` nobody sees; when Cloudflare wants the person to act, the view appears in the middle of the window, 340 by 120 pixels under a "Forge Images" title with a close button, as the desktop's window does. A closed view, or no answer in two minutes, fails the Forge attempt, and the app goes on to its next provider as on the desktop.
- **No in-app installer.** `downloadAndInstallUpdate` is refused: Orivon installs a new release of the app, not the app.
- **An embed is shown in a `<webview>`, so a site that checks which page frames it can refuse.** Twitch's player is given the app's host as its `parent` and has no parent frame to confirm it. The sites an embed can open are the ones in `web.embed.origins`; one that is not there stays blank. The window of a board's spam-blocker challenge draws the challenge page in an `<iframe>` too, and it is shown the same way for the challenge's own address (`https://spamblocker.bitsocial.net`); a board owner's own address for the challenge stays blank, though "Finish Challenge" still answers.
- **A "settings upgrade available" dialog appears on a new account** and offers two HTTP routers that are newer than the desktop preload's list. It is upstream's own check against its current defaults.

The sections below are for people working on the build.

**What this is.** 5chan's desktop renderer is the Vite build its web app is made of (`vite build` with `PUBLIC_URL=./`, which `electron:build` runs before Electron's packager takes the folder). Two window values make that build the *desktop* app at run time (`src/lib/p2p-browser-config.ts`): `window.isElectron` and `window.electronApi.isElectron`. With them the page uses a Bitsocial node over RPC; without them it runs libp2p in the page. This port sets both inside Orivon, with the other values `electron/preload.mjs` sets, so the same page needs only a node behind port 9138.

## Running it

```bash
orivon-port run 5chan      # clone at the pinned commit, build, prepare, serve on 127.0.0.1:8884
orivon-port test 5chan     # or: npx vitest run apps/5chan
```

The build runs upstream's pinned yarn (4.17.1, fetched with `npx`, never `corepack enable`) with `ELECTRON_SKIP_BINARY_DOWNLOAD=1` and `--mode=skip-build`, so no native module is compiled. The build step is `generate-asset-manifest.js` and then `vite build`, which is `yarn build` without its `sync:directories` step: that step fetches the board lists from GitHub, and the lists are committed in `src/data/5chan-directories/` at the pin, so the build uses those and needs no network. `VITE_COMMIT_REF` and `VITE_LATEST_RELEASE_COMMIT_REF` are set to the pinned commit, so the build needs no `git ls-remote` either.

Open `http://127.0.0.1:8884` in Orivon and accept the prompt. `5chan.orivonstack.eth` works too once the shell is launched with `orivon-port names`' output (the top-level [`README.md`](../../README.md), "Opening it by name instead of by port").

## The seam

`electron/preload.mjs` sets four window values and one object, `window.electronApi`, of 9 members. How this port answers them:

| Member | Answer | State |
|---|---|---|
| `isElectron` (window and `electronApi`) | `true` | works |
| `defaultPkcOptions` | the RPC address `ws://localhost:9138/<key>` and the preload's four HTTP routers | works; the node behind it is the one `node-start.js` starts |
| `defaultMediaIpfsGatewayUrl` | `http://localhost:6473` | works; the node's gateway socket |
| `pkcRpcAuthKey` | the same key as in the RPC address | works (unused by the renderer, kept as the preload has it) |
| `copyToClipboard` | the async clipboard; `{ success, error }` | works |
| `getPlatform` | `{ platform: 'orivon', arch: 'orivon', version: '' }`, the object the preload's `get-platform` returns | works; the updater finds no installer and offers no update |
| `getNodeReachability` | a `POST` to the kubo API's AutoNAT route; `'public'`, `'private'` or `'unknown'` | works: the call is answered by the node's page API (see "The desktop's kubo calls"), with what a reader can do according to the node's own `reach` (a limited relay or an untried punch is not `public`) |
| `getPathForFile` | a token mapped to the `File` the page holds | works |
| `automateUploadMedia`, `automateUploadGeneratedMedia` | catbox: a routed request with the form catbox takes. imgur and imgbb: the host's upload page in a `<webview>` nobody sees (`webview-upload.js`), with the metadata removed first on the path route | works |
| `getForgeTurnstileToken` | the token of Cloudflare's Turnstile widget, run on `http://localhost:50219` in a `<webview>` (`webview-turnstile.js`); rejects with the desktop's error texts | works: a token for Cloudflare's always-pass test sitekey in a real shell run; the real Forge sitekey gets Cloudflare's "Verify you are human" checkbox, which only a person passes (see the design note on the Turnstile token) |
| `downloadAndInstallUpdate` | rejects `shell-owned` | refused |

**1 of 9 calls `orivon.*`.** `getForgeTurnstileToken` opens a listener with `orivon.net.listen` to serve the widget's page. The members that need no node are the page's own: the clipboard, `fetch`, `localStorage`. The upload members use the page's `<webview>` element, which the `web.embed` grant allows. The node's page module forks the Worker with `child_process.fork`, and `node-start.js` starts nothing until the page has its permissions (`window.orivon.fs` exists); the bridge's own members do not touch it.

A refusal rejects instead of throwing, because the preload's versions return promises and a call site outside an async function has no `try` to catch a throw.

## Design notes

**The desktop values are set only inside Orivon.** The page picks its runtime from `window.isElectron`, from `electronApi?.isElectron` and from single `electronApi` members (`getForgeTurnstileToken` among them), so outside Orivon none of them may exist. The bridge's first statement is a `return` unless `window.orivon` is an object with a numeric `version`, which every Orivon tab has (v0.1.0 included) and which the hint tests too. The `return` is legal because `compose.ts` splices the file inside a function of its own, so the installer after it never runs: no `isElectron`, `electronApi`, `defaultPkcOptions`, `defaultMediaIpfsGatewayUrl` or `pkcRpcAuthKey`, no key in `localStorage`, and the service worker is left alone. `node-start.js` makes the same test: outside Orivon it leaves `fetch` as the browser made it and starts no node, and it still gives the module entry its type back at once, so the app runs. The renderer then merges its own web defaults, as upstream's web version does. The hint is tier 1 there, a pill that does not hold the page back.

**The RPC key lives in `localStorage`.** The desktop keeps a 40-character key in a file beside the node's data and puts it in the URL the page connects to. The page has no main process to hand it over, so the bridge makes one (40 characters of a 62-character alphabet, rejection sampling over `crypto.getRandomValues`), stores it as `orivon.pkcRpcAuthKey`, and reads it back on the next load; a stored value that is not 40 letters and digits is replaced, and storage that throws leaves a key for that load only. The node package reads the same key from the same place when it starts the node. The key is a bearer secret for the RPC socket on a loopback port; it stays in this origin's storage.

**No service worker inside Orivon.** Upstream's page registers `sw.js` through `registerSW.js`. The desktop never has one (a `file:` page cannot register it), and a worker here would keep serving one release's files, the bridge among them, after Orivon installs the next, which is the cache-across-a-republish failure. So inside Orivon the bridge removes `serviceWorker` from `navigator`, which the generated registration and the app's own checks both test for, and unregisters a worker an earlier load registered. The worker file stays in the tree and is never used there. No upstream byte is edited. In a real shell run `'serviceWorker' in navigator` is `false`. Outside Orivon the bridge has returned before this, and the worker registers as it does in upstream's web version: `registerSW.js` registers `./sw.js` with scope `./`, and the built `sw.js` precaches relative URLs (`assets/...`), so on a path gateway (`/ipfs/<cid>/`) it takes the app's own folder as its scope and finds its files there (the plain-browser check loads the tree at `/` and under `/ipfs/<cid>/`, and the worker activates in both).

**The `/#` redirect.** Upstream's page has an inline script that sends a path with no hash, such as `/b/catalog`, to `/#/b/catalog` from the root of the host. It cannot run inline under the served policy, and moved unchanged it would send a deep link on a path gateway out of the app's folder. The hook writes it again as `orivon/inline-script-3.js`: the same test, with the app's folder taken from where that file is itself loaded (`new URL('../', document.currentScript.src)`), so at the root of a host it does what upstream's does. The other five inline scripts (the stats prefetch, the translation and route preloads, the theme class and the static-shell paint) move byte for byte, each where it stood; the JSON data blocks are not code and stay. The hook throws unless it finds six inline scripts and exactly one redirect.

**`getPlatform` returns the object.** `app-update.ts` reads `{ platform, arch }` and looks for a release asset whose name matches. The platform is `orivon`, which matches none, so the check offers no update. A string here would make the updater read `undefined` for both.

**The node link.** The desktop sends exactly `http://localhost:50019/webui/` to the system browser. Here a capture-phase listener on `click` and `auxclick` stops that navigation and opens `orivon/node/index.html`, served with the app, in a new tab. That page's frame, wording and look are 5chan's own (its built stylesheet and variables, in `hooks.mjs`), and it wears `yotsuba`, the theme 5chan gives every page that is not a board (home, FAQ, rules, blotter, account data) whatever style the person chose (`src/hooks/use-theme.ts`: a stored style applies to a board and to the all, subscriptions, mod and search views only), so it reads no stored theme; what it draws is the node app's dashboard module, `node-dashboard.js` of the node bundle, which `bridge/node-dashboard.js` mounts with this app's name and the two sections it offers, the board manager and the listing. `node-start.js` finds the node already answering, and the module draws the numbers the node's page API gives (state, peer id, peer count, reachability, repository size, the two sockets) every five seconds. Being a second page of the origin, it also keeps the node running across a reload of the board's page.

**The board manager screens.** Under the node's numbers the dashboard lists each board the node hosts, as a card: whether its manager is on, its state and last error, how many threads it has archived, what happens to a thread past the limit (archived, or deleted at once on a board whose community sets `features.noArchive`, which a board owner sets in 5chan's own Board Settings: the dashboard shows it and says where), and three limits in a board owner's words (archive the oldest thread when the board has more than N threads; stop a thread moving up the board after N replies; delete an archived thread after a length of time), each with the default it uses while the field is empty. A second form sets the same three for every board that does not set its own. The cards come from the node's control channel (`handle.manager`, `apps/bitsocial-node/README.md` section The board manager); a node with no board manager, such as an older one another tab started, shows no section. The screens add nothing to 5chan's own pages: the dashboard is reached only through the link 5chan draws.

**The listing screens.** The dashboard also lists each board the node hosts as a card that gets it onto 5chan's home page, which 5chan has no screen for: a choice of directory from the lists on GitHub (`bitsocialnet/lists`, read live as the app reads them), what the board meets and misses of that directory's requirements in a board owner's words (the poster-ID mode, safe for work, links to media, no gallery, a challenge that holds a new poster for a moderator, the directory's rules), and, with the name that owns the board, a request signed with the board's own key. "Open on GitHub" opens the lists' new-issue form with the request filled in, and sends nothing: the person submits it there. It reaches only github.com and raw.githubusercontent.com, which the manifest's `https` grant already covers. The check is the node app's own code (`apps/bitsocial-node/page/dashboard/listing-requirements.js`), written fresh against 5chan's rules for hosting a directory; the node app's README, sections The listing calls and The node dashboard, has the rest.

**The name screen.** The dashboard also gives each board a card for naming it, which 5chan has no help for: its Board Settings is an editor of the board's settings as JSON, where the owner can type a `.bso` or `.eth` name as the `address`, and it shows no record to set and checks nothing. The card shows the record the name needs (the text record `bitsocial` of the ENS name, holding the board's public key) with a copy button for each part, checks that the name points at the board as the node's own name resolvers read it, and, on a page that has a wallet, prepares the transaction that sets the record and sends it only when the person presses the button that asks the wallet. When the name points at the board it says to set the address in 5chan's Board Settings (the "address" line): the card changes no address, since 5chan's own settings do. The calls and what a name is are in the node app's README, sections The name calls and The node dashboard. It reads Ethereum through the node, so the manifest needs nothing new.

**The page starts the node.** `node-start.js` calls the node app's page module (`node-client.js`, the node's own build output) with this app's ports and the key the bridge made. The module tries `ws://localhost:9138/<key>` first and uses a node that answers; otherwise it forks the Worker (`node/server.mjs`), which runs Orivon's IPFS node, the kubo facade, the gateway socket and pkc-js's RPC server behind the key guard, and resolves once the RPC socket listens. Nothing starts on a page that has no permissions yet or is not isolated (`window.orivon.fs` is absent until the person has answered the consent prompt), and the page reloads after the answer, so the first load of the first run does not leave a Worker behind. A start that fails is made again after 4, 8, 16 and 30 seconds, five starts in all, and `ready` settles with the handle of the first that works, or with `null` and the last reason after the fifth; it never rejects. The handle is `window.orivonBitsocialNode`, whose `error` holds the reason once the fifth start has failed. The key is read from the bridge's `window.pkcRpcAuthKey`, or from this origin's `localStorage` on a page the bridge did not run on (the dashboard).

**The bundle is shown while the node starts.** The RPC client in the bundle (pkc-js, `clients/rpc-client/pkc-rpc-client.js`) gives its connection 20 seconds from its first call (`_timeoutSeconds`, line 62; the wait is the `pTimeout` at lines 195 to 207), then sets its state to `failed`, emits `error` and rejects the calls that waited, and the community hooks never ask again, while its WebSocket goes on retrying. A connection that opens inside those 20 seconds costs nothing, and a call sent on it waits 300 seconds for its answer (`_callTimeoutMs`, line 67; the `pTimeout` at lines 171 to 176, which starts once the connection is open); `rpc-websockets` under it sets no timer on the calls the client sends (it passes none) or on an open connection. So the hook types the bundle's module entry `orivon-held-module`, a type no browser runs, and `node-start.js` gives it back its own type (every attribute kept, `type=module`) as soon as the page is parsed, on every launch: whether the node's files are on this computer or have still to arrive over the IPFS network, the app is drawn without waiting for the node, and `node-start.js` stands in for the node's RPC socket until it answers. The entry is released while the node starts, across its retries, and when every start has failed. While the node starts, `window.WebSocket` is a proxy that treats only the node's own address (`ws://localhost:9138/<key>`) differently: the socket the bundle makes there is reported open at once and what the page sends on it waits, and the real socket is opened when the node has answered (every event it brings is handed on, and what waited is sent in order) or failed to start. The socket is open and not left CONNECTING because the app takes an RPC that is not connected for a page with no node of its own: the app's "settings upgrade available" dialog opens over it (its two default HTTP routers are the ones the preload's four lack), and "create your own community" sends the person to a download page. Every other socket is the browser's own, and so is every socket once the node has answered. A start that is refused for half a minute (the page was opened again within about that time of the last one closing, which Orivon v0.1.0's shell answers with `revoked`) or a verifier that reads the node's files again costs the app time and not its connection; a node that answers after 270 seconds, when the calls that waited (300 seconds) are about to time out, makes the page load once more, once per tab. A page that has no bundle to release, the node dashboard, says "Starting your Bitsocial node..." once the wait is noticeable (with the file it is on, when a first start has failed and the node's files are read again); if every start fails, the app shows its own connection error after the last retry. A page with no permissions, or outside Orivon, releases the entry at once and stands in for nothing.

**The desktop's kubo calls are answered in the page.** 5chan's stats panel and its reachability check call `http://localhost:50019/api/v0/` (the kubo API the desktop's main process runs) for `id`, `swarm/peers`, `stats/bw`, `repo/stat`, `swarm/addrs/autonat` and `version`. Nothing listens on 50019 in this build: a kubo API that any app granted that port could drive would hand it the node. `node-start.js` wraps `window.fetch` instead: a request to either spelling of that origin never leaves the page. A path under `/api/v0/` goes to the node's page API (`POST /orivon/api/<call>` on the gateway socket, with the RPC key as a bearer token, which answers those six calls and refuses every other with 403); any other path of that origin (the web UI) is 404. A page of another origin cannot use either without the key: the RPC socket refuses a path that is not `/<key>` (a dial with no key or a wrong one closes with 1006), and the page API refuses a request with no key (401) and one whose `Origin` is not an origin the app named (403). The key is the only guard of the RPC socket: a page of any origin that holds it can open the socket, as on the desktop, where it is the only guard too. The page API is on the Worker's socket and not on the Worker's message channel because a page that reused a node, such as the reloaded page, has no handle on the Worker that another page started. `stats/bw` is the node's own count (`TotalIn`, `TotalOut`, `RateIn`, `RateOut`) when its `/health` names `bandwidth`; otherwise it answers null totals, and 5chan shows them as unknown.

**The node is a pinned build output, not imported code.** `build/fetch-node-bundle.mjs` runs after the app's build (`build.also`) and copies `node/` (the Worker's loader `server.mjs`, its packed script and `sqlite3.wasm`), `node-client.js`, `node-dashboard.js` and `bin/` (the IPFS node component, its packed program and its licences) from a build of `apps/bitsocial-node` (`BITSOCIAL_NODE_BUNDLE_DIR`, or that build's own output folder) into the served tree. Each file must match its size and sha256 in `build/node-bundle-pin.mjs`, and the files under `bin/` must be the component `apps/bitsocial-node/build/node-component-pin.mjs` pins. A mismatch fails the build with the way to move the pin on purpose (`node build/fetch-node-bundle.mjs --pin` after a rebuild of the node). Nothing of the node app is read when the page runs: the copy is this app's own files, and two apps that run the node carry one copy each.

**imgur and imgbb run as the desktop's hidden window does, in a `<webview>` nobody sees.** The desktop opens the host's upload page in a window that is never shown, puts the file on the page's file input, clicks submit, and reads the link off the page every 500 ms (`electron/media-upload-recipes.js`, `media-upload-automation.js`). `webview-upload.js` takes each step and each selector, message and timeout from there, so the app's own provider order, the blocked-page fallthrough and the error texts its orchestrator reads (`parseAttemptMetadata`) behave as on the desktop. What differs is the means. The element is attached on `about:blank` and then sent to the page, which makes a refused origin reject the load instead of ending the element. The page is another site's, so the file reaches its input from inside it: the bytes are sent in pieces of a mebibyte through `executeJavaScript`, put together as a `File`, set on the input with a `DataTransfer`, and `input` and `change` fire, which is what a chosen file fires. The click is the page's own `element.click()` with a user gesture, which imgbb's button accepts; a real mouse event (`sendInputEvent`) is what the desktop's click is, and this build does not use it. A poll that fails once (the page replacing itself after the click) is "no link yet". The element is a fixed 800 by 600 box at the top left, fully transparent, not clickable and muted, and it is removed when the upload ends, however it ends. The two uploads and the embeds draw on the same grant, `web.embed`: only the origins in `orivon.json` load, and a document at any other origin is refused, which for an upload page that redirects elsewhere is a failed load.

**imgur is read from its post page.** imgur's page does not have the shape the desktop's selectors expect: choosing a file uploads it at once, the page moves to `/a/<id>`, the copy-link field there holds the post's address (`PostShare-copyLink--input`, not a file link) and no `i.imgur.com` anchor exists, so the desktop's four candidates find nothing and its recipe times out. `webview-upload.js` keeps the desktop's candidates first and, only when none answers and the page's path is a post (`/a/` or `/gallery/`), reads the one `<img src="https://i.imgur.com/...">` the page shows. The submit button, which exists only after the upload and opens the page's own upload popup when clicked, is looked for after the file as on the desktop; where there is none, the upload goes on to wait for the result and gives the desktop's "No submit button found" message only if none comes. The path check is there because the upload page itself shows other pictures from the same host.

**Metadata leaves the file first, on the path route.** The desktop's main process strips camera and location metadata from a JPEG, PNG or WebP before the upload page sees it (`electron/strip-media-metadata.js`), because the bytes of a path never pass through the renderer; the renderer strips what it makes itself (a drawing, a catbox or Forge upload) before it sends it. A page has no path, so `getPathForFile` hands the renderer a token and the bridge holds the `File`: the token route strips it (`stripMetadata` in `webview-upload.js`, written from the formats, not copied) and the generated-bytes route does not, as the desktop's two handlers differ. A rotation survives as the one small tag it needs. A file that is not one of the three, or that cannot be read to its end, is uploaded as it is, so stripping never blocks an upload.

**An embed frame stays in the page; its element is added beside it.** The built page renders each click-to-open embed as an `<iframe>` its component owns, and a framework removes a node from its own parent: replacing the frame with another element would make that removal throw. So `webview-embeds.js` hides the frame (`display: none`) and puts a `<webview>` after it with the frame's class, so the app's own styles size it, a zero-weight 100% by 100% fallback for the frame's own width and height hints, its title, and its address. The address is the frame's `src`; the three embeds that carry inline content (Reddit, TikTok, Instagram: a quote block and the site's widget script) are shown from a `data:` page that holds the same content, and the widget then opens a frame of its own site, which is why those three sites are in `web.embed.origins` too. A frame that sends its own origin as the referrer (YouTube's) gets the app's origin as `httpreferrer`. A window an embed asks for opens as a tab, for a secure address only, as the desktop sends one to the system browser. A frame removed by the app takes its element with it, and one whose `src` the app changes is followed. Outside Orivon `<webview>` is an unknown element and nothing here runs.

**The Turnstile token is the desktop's, with its own window made of a `<webview>`.** Turnstile issues a token only to a hostname the sitekey allows (for Forge's: `5chan.app` and `localhost`), so the page's own origin can never get one and the desktop's main process runs the widget in a window it opens on `http://localhost`. `webview-turnstile.js` does the same in three parts. **The page is served by the page that asks, not by the node's Worker.** On a call it opens `orivon.net.listen({ port: 50219, scope: 'local' })`, answers `GET` and `HEAD` of `/forge-turnstile` with the widget's page (404 for any other path, 405 for any other method, a request head over 8 KiB or silent for 5 s closed), and keeps the listener open for ten seconds after the last call in flight ends, so calls that follow one another reuse it; a call that finds the listener closing waits for the port to be free. Nothing is added to the Worker, so the node bundle and its pin do not change, and a Worker that is reused by another page serves nothing for it. A second page of 5chan that finds the port taken goes on to load it, because the first page's listener answers. **The page is shown in a `<webview>` at the exact origin `http://localhost:50219`**, loaded after the element is attached on `about:blank` and read with `executeJavaScript`: `window.turnstileResult` for the answer and `window.turnstileInteraction` for the moment Cloudflare wants the person to act. The load is not awaited (the desktop waits for `dom-ready` for the same reason: the load ends only once Cloudflare's script and frame have), and the page's own clocks (15 s for the script, 30 s for a token, 120 s once the person is asked) and the 180 s backstop are the desktop's. **The view is invisible until Cloudflare asks.** Then it moves to the middle of the window at 340 by 120 pixels under a 28-pixel title bar that says "Forge Images" and holds a close button, the one visible change this port makes, standing for the desktop's window and its close box; closing it ends the call as closing the window does. The widget's page is written from what the desktop's page does, with the desktop's options (`appearance: 'interaction-only'`, `retry: 'never'`, `refresh-expired: 'never'`) and error texts, so the preload's `Error(error)` and 5chan's "Turnstile check failed: ..." read as on the desktop. The page is served with a policy of its own: `default-src 'none'`, its one inline script admitted by a nonce made for the response, and Cloudflare's origin for the script and its frame. **Cloudflare's frame is a document of another origin inside the shown page**, so `https://challenges.cloudflare.com` is in `web.embed.origins` beside the page's own; a subresource is the page's business, and Forge's API and media hosts are reached by `https.connect` as any host is.

**What differs from the desktop's window.** Its partition is in memory and Electron's own user agent is kept; this view lives in the app's `persist:embed-` partition, which the shell chooses for every `<webview>`, so Cloudflare's storage for `localhost:50219` survives a restart of the shell. The desktop's window is centred on the screen and a child of the app's; this one is centred in the app's window. A reload, a crash of the page and a closed view end the call with the desktop's three texts. A shell that never attaches the view fails the call after 30 s with `Turnstile page failed to load: the page could not be shown`, which has no desktop counterpart. The grant names the exact origin `http://localhost:50219`, which the shell shows whatever listens there, so a program of this computer that holds the port while no page of 5chan does could show its own page in the view; the view has no `orivon.*` and a program that can bind a loopback port can already do what that page could. A `http://*.localhost:50219` pattern would show only this app's own listener; its host name is not `localhost`, and *provisional*: no run has asked Cloudflare whether Forge's sitekey allows it.

**The upload page and the helper scripts are not in the bridge file.** A bridge is one spliced script and the size limit is 500 lines, so the three `webview-*.js` files sit beside it and `hooks.mjs` copies them into the served tree and loads them last in the head. The bridge reads `window.orivonWebviewUpload` and `window.orivonForgeTurnstile` when a member is called, not when it is installed, and rejects with a plain message when one is missing. Nothing in these files names 5chan (the Turnstile script takes its port from the bridge), so another port of a Bitsocial client can take them as they are.

**The Worker's gateway counts for `img-src` and `media-src`.** An app with a `tcp.listen.local` grant is served with `http://localhost:*` and `http://127.0.0.1:*` in both directives (measured in the v0.1.0 shell: `img-src 'self' data: blob: http://localhost:* http://127.0.0.1:* orivon-file: https:`), so the gateway on 6473 needs no grant of its own and the build leaves the page's policy as it is. A load of the gateway's address raises no violation for `<img>`, `<video>` or `<audio>`; an `http://` image of a host that is not loopback does.

**Ports.** Every app that runs a node needs its own, so two of them run at once. 5chan: RPC 9138, gateway 6473 (both the desktop's own), node API 50119, Turnstile page 50219, peer range 4001-4010; 50019 is the desktop's kubo API port, which the page answers without a socket (see above) and the manifest names nowhere. The node API and the Turnstile ports are this port's own: they are named in `tcp.listen.local` and, for the Turnstile page, in `web.embed.origins`, because `*:*` never reaches loopback and each port is named. The connect list names the RPC, gateway and node API on `127.0.0.1` and `localhost` (the page dials the first two, the Worker the third) and two DNS resolvers (`1.1.1.1:53`, `1.0.0.1:53`) the node's own lookups use, as the node app's manifest does. seedit uses the next block (9148 and so on), so neither collides with the other.

**`fs.quotaBytes` is 10 GiB.** It is the size Kubo's datastore is capped at by default (`Datastore.StorageMax`, 10 GB), which the node's blockstore, the pinned community data and the hosted communities' databases share, and the node's SQLite files live in it. *Provisional*: a real use moves it.

**`crossOriginIsolated: true`.** The node's page module needs it, as the node app's manifest declares it: the Worker's SQLite engine is WebAssembly with shared memory. Its cost is the two headers on every response: cross-origin subresources load without credentials (`credentialless`), and a popup the page opens is in its own browsing context group. `node-start.js` starts nothing on a page that is not isolated.

**`https.connect` is `*:*`.** Posts link any site, and the app's own requests go to its stats provider, name resolvers, router lists and catbox. Orivon's routed request replaces the header rewrite the desktop's main process does: it sends no `Origin` unless the app sets one.

## What it needs from orivon-mvp

Catalogue ids from `test/app-behaviours/catalogue.md` that this port relies on; a red `[app:<id>]` test is this port's breakage:

- `routed-websocket-reaches-granted-loopback-port`: the RPC connection to `ws://localhost:9138`.
- `routed-fetch-reaches-granted-hosts`: posts, the stats provider, name resolvers and catbox are reached with no CORS check.
- `routed-fetch-sends-no-origin-by-default`: the node's APIs and catbox refuse a foreign `Origin`.
- `routed-fetch-sends-formdata`: the catbox upload.
- `routed-fetch-loopback-grant-covers-both-spellings`: the kubo API and the gateway answer on `localhost` and `127.0.0.1`.
- `wildcard-host-never-reaches-loopback`: why every loopback port is named.
- `page-media-from-own-listener`: the gateway's images and video, which load because an app with a listen grant is served the loopback sources in `img-src` and `media-src`.
- `localstorage-survives-restart` and `indexeddb-survives-restart`: the RPC key, the account and the caches.
- `cross-origin-isolated-when-declared`: the isolation the manifest asks for.
- `clipboard-write-without-prompt`: the copy buttons.
- `window-open-noopener-opens-tab`: outbound links and the node link.
- `webview-popup-reaches-the-app`: a window an embed asks for, which `webview-embeds.js` opens as a tab.

Behaviours of `web.embed` that the catalogue does not state and the two scripts rely on (measured in a real shell, with a loopback page standing for each site and against the real imgbb, imgur and YouTube): a `<webview>` that is fixed, transparent, not clickable and muted still loads its page and reports `document.visibilityState` as `visible`; `executeJavaScript` runs in it, with and without a user gesture; a file set on a page's `<input type="file">` with a `DataTransfer` fires `input` and `change` and the page uploads it; `loadURL` of a document at an origin outside `origins` rejects; the `httpreferrer` attribute is the `Referer` the shown page's request carries and what `document.referrer` reads there; a `data:` page is admitted, and a widget script it loads from a granted origin runs. None has a row.

Behaviours of `web.embed` and `orivon.net.listen` that the Turnstile script relies on, measured in a real shell run with Cloudflare's own widget: a page the app serves from its own `orivon.net.listen` (a hand-written HTTP/1.1 answer per connection, `Connection: close`) loads in a `<webview>` at the exact origin `http://localhost:<port>` when the manifest names that origin, with no local pattern; the widget's frame loads from `https://challenges.cloudflare.com` once that origin is in `origins`; a `<webview>` inside a fully transparent, unclickable box behind the page reports `document.visibilityState` as `visible`; `executeJavaScript` of an expression that is a promise waits for the promise, two minutes in the run where nobody answered Cloudflare's checkbox. Against the real Forge API from the page (`https.connect` `*:*`): an XHR with an upload listener, as `uploadToForge` sends it, gets the API's own HTTP answer (a refused token is `403 turnstile_failed`), so the request is not stopped by a missing CORS answer. None has a row.

Two behaviours the catalogue does not state are relied on: a classic script the app serves can remove `navigator.serviceWorker` from the page before the bundle runs (measured in a real shell run, not by CI), and a `ws://localhost:<port>` dial reaches a listener bound on `127.0.0.1` only (the shell's dial tries both address families; no listener was behind it in the run). Neither has a row.
